## Key gaps to resolve before implementation of later stories

1. **`transactions` table is missing 7 designed columns**: `status`, `transaction_origin`, `parent_transaction_id`, `reversal_of`, `reversal_reason`, `reversed_by`, `correction_of`, `corrected_by`, `created_at`, `updated_at`
2. **`statements` table is missing 3 designed fields**: `status` enum needs 4 new values, `declared_total`, `file_type`
3. **`app_settings` missing**: `review_before_commit`
4. **Hard delete must be removed** before any reversal story ships — it bypasses the ledger immutability rule
5. **`GET /transactions` has no staged/reversed exclusion** — will silently include garbage rows once those features land
6. **PATCH does not implement reversal** — direct mutation of committed financial records

---

## Decisions (recorded 2026-07-18)

| Finding | Decision | Rationale |
|---|---|---|
| U1 `GET /statements` | **Keep, document** | Paginated (offset/limit); will be covered when statement-list story is written. Marked deprecated until then. |
| U2 `DELETE /statements/{id}` | **Keep, document** | Statements are file records, not ledger entries. Reversal rule applies only to committed transactions. DELETE of a statement (removes file + unlinks transactions) is correct file management. |
| S1 `DELETE /transactions/{id}` hard delete | **Queue for removal** | Violates ledger immutability. Remove route and replace with `POST /transactions/{id}/reverse` when Story 2.3 is implemented. |
| 22 UNIMPLEMENTED stories | **Continue design pass** | Audit E3–E9 before touching code. |

**Note on mutation semantics clarified during audit:**
- `DELETE /statements/{id}` → file management, hard delete is correct
- `DELETE /transactions/{id}` → ledger violation, must become `POST /reverse`
- `PATCH /transactions/{id}` on financial fields → reverse + create (Story 2.2)
- `PATCH /transactions/{id}` on `category_id` → direct update + audit_log (Story 2.2)
